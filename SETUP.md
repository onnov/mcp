# GitHub MCP: минимальная разработка

Реализация целиком в `main.go`. Она основана на текущем `onnov/mcp`: порт
`127.0.0.1:8181`, `runtime.GOMAXPROCS(2)` и SDK v1.8.0 сохранены.
Существующие `go.mod` и `go.sum` менять не нужно. Новые зависимости не добавлены.

## Инструменты

| Инструмент | Действие |
|---|---|
| `get_repository` | Метаданные и основная ветка |
| `list_directory` | Список файлов |
| `read_file` | Текст файла и его blob SHA |
| `create_branch` | Новая ветка `mcp/...` от существующей ветки |
| `write_file` | Создание или замена одного файла с немедленным коммитом |
| `compare_refs` | Diff между ветками или коммитами |
| `create_pull_request` | Создание PR, в том числе черновика |

Это работа через GitHub REST API. Локального checkout, staging area и команды
`git push` нет: `write_file` сразу создаёт коммит в удалённой ветке.
Установленный на хостинге `git` не требуется.

Без настройки OAuth сервер предоставляет четыре инструмента чтения, включая
`compare_refs`. Инструменты записи появляются только после настройки OAuth
и списка разрешённых репозиториев. В режиме OAuth весь `/mcp` требует входа.

## 1. Собрать

Заменить `main.go` в существующем проекте. Для тестирования положить рядом
`main_test.go` из архива. Этот файл не нужен для запуска сервера.

```sh
gofmt -w main.go main_test.go
go test ./...
go vet ./...
CGO_ENABLED=0 go build -ldflags="-s -w" -o github_public_mcp main.go
```

В среде, где подготовлен этот файл, нет Go: компиляция, `go test` и `go vet`
здесь не выполнялись. Тесты используют подмену HTTP-транспорта, не отправляют
запросов на GitHub и не изменяют реальные репозитории. Первый настоящий вход
через GitHub и подключение ChatGPT также нужно проверить после развёртывания.

## 2. Создать GitHub OAuth App

Открыть <https://github.com/settings/developers> → **OAuth Apps** → **New OAuth App**.

| Поле | Значение |
|---|---|
| Application name | Например, `ghf development` |
| Homepage URL | `https://mcp-msk.v02.ru` |
| Authorization callback URL | `https://mcp-msk.v02.ru/oauth/github/callback` |

Получить **Client ID** и создать **Client secret**. Это значения
`GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET` для процесса Go.

Сервер запрашивает GitHub scope `public_repo`. У вошедшего пользователя должны
быть права записи в выбранный репозиторий. Поддерживаются только открытые
репозитории; сервер дополнительно проверяет это перед чтением и записью.

Документация: <https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps>
и <https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps>.

## 3. Настроить окружение процесса Go

Пример для твоего домена и `onnov/mcp`:

```sh
export MCP_PUBLIC_URL='https://mcp-msk.v02.ru'
export GITHUB_CLIENT_ID='CLIENT_ID_ИЗ_GITHUB'
export GITHUB_CLIENT_SECRET='CLIENT_SECRET_ИЗ_GITHUB'

export MCP_CLIENT_ID='ghf-chatgpt'
export MCP_CLIENT_SECRET="$(openssl rand -hex 32)"
export MCP_ALLOWED_USERS='onnov'
export MCP_WRITE_REPOS='onnov/mcp'

./github_public_mcp
```

Вместо `onnov` укажи логин аккаунта, через который будешь входить в GitHub.
Допустимы списки через запятую, например `owner/repo1,owner/repo2`.
Все разрешённые пользователи получают доступ к общему списку репозиториев,
но GitHub отдельно проверяет права каждого пользователя.

`MCP_CLIENT_SECRET` — отдельный случайный секрет **между ChatGPT и MCP**.
Его нужно сохранить и затем ввести в настройках плагина. Не генерируй его
заново при каждом перезапуске. `GITHUB_CLIENT_SECRET` остаётся на сервере.
Не записывай секреты в исходники и репозиторий.

Если запускаешь бинарник через панель хостинга или менеджер процессов,
эти переменные нужно задать именно для того процесса. Команда `export` в другой
SSH-сессии не изменяет окружение уже запущенного сервера.

Здесь **два разных callback**:

1. GitHub возвращает пользователя в `/oauth/github/callback` на твоём сервере.
2. Твой MCP возвращает пользователя в ChatGPT. По умолчанию используется
   `https://chatgpt.com/connector_platform_oauth_redirect`.

Сервер публикует поддержку issuer identification и возвращает `iss`.
Если интерфейс подключения показывает иной callback ChatGPT, перед запуском
задай его точное значение в `MCP_REDIRECT_URI`. Callback GitHub при этом прежний.

Документация ChatGPT OAuth: <https://developers.openai.com/plugins/build/auth>.

## 4. Apache и проверка адресов

Твоё правило остаётся подходящим для проксирования всех путей:

```apache
RewriteRule ^(.*)$ http://127.0.0.1:8181/$1 [P,L]
```

Для OAuth снаружи должны быть доступны не только `/mcp`, но и `/.well-known/*`
и `/oauth/*`. Проверь, что другие правила хостинга не перехватывают эти пути
и что до Go доходит HTTP-заголовок `Authorization`.

`-public-host` для твоей схемы не нужен. `MCP_PUBLIC_URL` нужен: из него строятся
внешние OAuth-адреса, независимо от внутреннего Host после Apache.

```sh
curl -i https://mcp-msk.v02.ru/healthz
curl -i https://mcp-msk.v02.ru/.well-known/oauth-protected-resource
curl -i https://mcp-msk.v02.ru/.well-known/oauth-authorization-server
curl -i https://mcp-msk.v02.ru/mcp
```

Ожидается: `healthz` → `200` и `ok`; оба metadata-адреса → `200` и JSON;
`/mcp` без авторизации → **401** с `WWW-Authenticate`. Последнее подтверждает,
что OAuth включён. `403` обычно означает несоответствие Host/Origin;
`404` на metadata-адресах — проблему маршрутизации или старую версию бинарника.

## 5. Подключить в ChatGPT

В настройках существующего подключения переключить авторизацию на **OAuth**
либо создать отдельное подключение для этой версии сервера:

| Поле | Значение |
|---|---|
| MCP URL | `https://mcp-msk.v02.ru/mcp` |
| Authentication | OAuth |
| OAuth Client ID | Значение `MCP_CLIENT_ID`, по умолчанию `ghf-chatgpt` |
| OAuth Client Secret | Сохранённое значение `MCP_CLIENT_SECRET` |

Если OAuth-поля спрятаны, открыть дополнительные настройки. Сервер использует
заранее заданный OAuth-клиент и не предоставляет dynamic client registration.
В поля плагина вводятся **MCP-реквизиты**, а не реквизиты GitHub OAuth App.
Если интерфейс не позволяет указать такой клиент, пришли видимые поля настройки:
потребуется адаптировать регистрацию клиента под этот интерфейс.

Подключить аккаунт GitHub, разрешить доступ и обновить список инструментов
подключения. После успешного входа сервер предлагает семь инструментов.

## 6. Первый рабочий цикл

Попросить модель, например:

> В репозитории onnov/mcp создай ветку mcp/test-readme. Прочитай README.md
> из этой ветки, добавь строку с описанием сервера и создай коммит. Затем покажи
> diff относительно main и открой черновой PR.

Порядок вызовов:

1. `get_repository`: получить основную ветку.
2. `create_branch`: создать `mcp/test-readme` от основной ветки.
3. `read_file`: указать `ref: "mcp/test-readme"`, сохранить возвращённый `sha`.
4. `write_file`: указать эту же ветку, полный новый `content`, сообщение
   коммита и `expected_sha` из предыдущего шага.
5. `compare_refs`: `base: "main"`, `head: "mcp/test-readme"`.
6. `create_pull_request`: эта же `head`, `base: "main"`, заголовок, `draft: true`.

`expected_sha` защищает заменяемый файл от перезаписи изменений, которые появились
после чтения. Для **нового** файла SHA не передаётся: GitHub отклонит такой запрос,
если файл уже существует. После конфликта нужно заново прочитать файл в целевой
ветке и согласовать изменения. После сетевого таймаута сначала проверь результат:
коммит, ветка или PR могли быть созданы до потери ответа.

## Ограничения этой версии

- Только открытые репозитории. Запись: только `MCP_WRITE_REPOS`, только ветки
  `mcp/...`, кроме основной ветки. Авторизация: только `MCP_ALLOWED_USERS`.
- Один файл — один коммит, UTF-8 без NUL, максимум 128 KiB.
- Нет удаления/переименования, атомарного коммита нескольких файлов, merge,
  force push, изменения `.github/workflows/` и запуска сборки или тестов проекта.
- Diff ограничен: максимум 300 файлов от GitHub; ответ разбит через `offset/limit`.
  Patch обрезается до 4 KiB на файл и 64 KiB на ответ; признаки неполного результата
  возвращаются явно. У бинарных файлов patch может отсутствовать.
- OAuth-сессии в памяти: один экземпляр сервера. После перезапуска требуется
  повторное подключение аккаунта. MCP access token действует до часа с обновлением;
  через 24 часа, либо раньше при истечении GitHub token, требуется новый вход.
- Это подготовленная реализация: компиляция и полный вход GitHub → MCP → ChatGPT
  ещё требуют проверки на твоём хостинге.
