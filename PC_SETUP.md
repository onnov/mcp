# PC MCP: локальная среда разработки

`cmd/pc-mcp` — второй, независимый MCP-сервер в этом репозитории.
Он запускается на вашем ПК. MCP и официальный **Go SDK OpenAI Secure MCP
Tunnel** работают внутри одного процесса, через in-memory MCP transport.
Отдельный tunnel-client, VPS, Apache, домен и входящие порты не нужны.
GitHub MCP `cmd/github-mcp` продолжает работать отдельно.

## Сборка и зависимости

Нужен **Go >= 1.27.0**: это требование закреплённого
`github.com/openai/tunnel-client v0.0.15`. При разрешённом `GOTOOLCHAIN=auto`
Go загрузит требуемый toolchain. Без сети установите его заранее.

```bash
git switch mcp/pc-development-server
make build-pc
```

Для выполнения команд на Ubuntu нужен **bubblewrap >= 0.12.0** и работающие
непривилегированные user namespaces, а также `/usr/bin/prlimit` (util-linux).
Проверьте `bwrap --version`.
Ubuntu-пакет может оказаться старее; установите актуальную версию из
доверенного источника вашей системы. Минимальная версия выбрана из-за
[CVE-2026-87766](https://github.com/containers/bubblewrap/security/advisories/GHSA-pxhw-h44j-8pfx).
Автоматического перехода к обычному, неизолированному `exec` нет.

Git, gh, компиляторы, интерпретаторы и инструменты тестирования устанавливает
владелец ПК. Сервер обнаруживает их и использует установленную среду; он не
устанавливает SDK автоматически. Файловые инструменты не зависят от bubblewrap.
Текущая Git-ветка читается непосредственно из HEAD, поэтому редактировать файлы
в обычном checkout можно и до настройки выполнения команд. Полный git status,
список веток и переключение требуют Git и работающей изоляции.

## Настройка туннеля

1. В [Platform tunnel settings](https://platform.openai.com/settings/organization/tunnels)
   создайте туннель. Для создания нужны организационные права **Tunnels Read +
   Manage**, для запуска/выбора — **Read + Use**.
2. Привяжите туннель к той организации Platform и тому пространству ChatGPT,
   где будете создавать плагин. Personal Platform organization сама по себе не
   делает туннель доступным в рабочем Enterprise/Edu-пространстве.
3. Получите runtime API key для клиента туннеля. Это отдельная настройка Platform,
   не ваш GitHub token и не пароль ChatGPT. Не отправляйте ключ в чат.
4. Подготовьте выделенный каталог проектов, например `/home/you/projects`.
   В нём могут быть любые вложенные проекты. Корень файловой системы и весь
   домашний каталог выбирать нельзя.
5. Запустите бинарник:

```bash
export CONTROL_PLANE_TUNNEL_ID='tunnel_...'
# Введите ключ без отображения и без его сохранения в истории команд:
read -rsp 'Tunnel API key: ' CONTROL_PLANE_API_KEY; echo
export CONTROL_PLANE_API_KEY

./pc-mcp --root "$HOME/projects" --toolchains /usr/local/go
```

`--toolchains` нужен, если SDK лежит вне стандартных `/usr`, `/bin`, `/lib`.
Go в `/usr/local/go` уже находится внутри `/usr`, его `bin` есть в sandbox PATH;
явный флаг в примере допустим, но необязателен. Для SDK в домашнем каталоге укажите **только его выделенную
папку**, например `--toolchains /home/you/sdk/go`, а не весь `$HOME`.
Несколько SDK разделяются запятой. Внутри sandbox их `bin` добавляются в PATH.

Можно экспортировать `PC_MCP_ROOT` и `PC_MCP_STATE` из
[.pc-mcp.env.example](.pc-mcp.env.example). Сам бинарник `.env` не читает:
если создали `.pc-mcp.env`, загрузите его в своей оболочке через
`set -a; source .pc-mcp.env; set +a`. Реальный файл исключён из Git.

В stderr сначала появится `starting outbound OpenAI tunnel`, затем, после
успешного обмена с OpenAI, `tunnel connected`. Туннель инициирует исходящие
HTTPS-запросы к `api.openai.com:443`; MCP не слушает сетевой порт на ПК.
Потерянное соединение восстанавливает официальный SDK. Пока ПК выключен,
спит или клиент не подключён, инструменты недоступны.

6. В ChatGPT → создание пользовательского MCP-плагина → **Connection: Tunnel**
   выберите созданный туннель или укажите его ID. Для этого частного сервера
   собственный OAuth не реализован: доступ контролирует Secure MCP Tunnel.
   Метод аутентификации MCP — **без дополнительной аутентификации**, если форма
   позволяет этот режим. Создайте плагин и подключите его к чату.

Если Tunnel отсутствует в форме либо список пуст, проверьте права, связь с
нужным пространством и разрешение администратора на custom MCP.
Сервер не обходит ограничения пространства. Secure MCP Tunnel предназначен
для частного подключения; публикация этого PC-сервера в общий каталог плагинов
не является частью реализации.

Это **один доверенный владелец / одна рабочая станция**, не многопользовательский
хостинг. Выбор каталога общий для этого экземпляра сервера. Все пользователи,
которым организация разрешила использование этого туннеля и плагина, получают
доступ к разрешённому дереву проектов. Ограничьте доступ до нужного владельца;
не раздавайте плагин всему пространству. OAuth-проверки конкретного GitHub ID
из GitHub MCP к PC MCP не применяются.

Официальные документы:
[Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels),
[встраивание Go SDK](https://github.com/openai/tunnel-client/tree/v0.0.15/examples/go-sdk-inmemory).

## Работа в чате

После подключения напишите: **«Открой выбор рабочего каталога ПК»**.
Модель вызывает `pc_open_workspace_picker`: карточка появляется в сообщении.
Само добавление плагина не обязано автоматически открывать карточку.

Карточка восстанавливает последний выбранный каталог и показывает текущую
фактическую ветку. Перемещайтесь по папкам, фильтруйте имена в открытой папке,
нажмите «Выбрать эту папку». Затем выберите текущую/другую локальную ветку либо
«Новая ветка» и подтвердите. Новая ветка создаётся от текущей; API-инструмент
также принимает другую локальную `base_branch`.

Если хотите выбирать текстом, попросите:

> Покажи дерево каталогов ПК. Для проекта `my-app` покажи ветки и создай
> `feature/my-task`, затем работай в ней.

Все пути инструментов относительны `--root`; `.` означает сам разрешённый корень.
Пути файлов и `cwd` команд относительны выбранному проекту. Для Git-проекта лучше
выбирать корень checkout. Если выбираете его подкаталог, команда получает весь
разрешённый checkout как `/workspace`, а cwd устанавливается в нужный подкаталог:
это позволяет Git и сборщикам видеть родительские `.git`/`go.mod`.

Один каталог state может использовать только один запущенный экземпляр сервера;
OS-lock освобождается при завершении процесса. Не запускайте несколько экземпляров
с разными state поверх одних проектов: они не разделяют блокировку checkout.

Выбор сохраняется в `selection.json` вне рабочих проектов, переживает новые чаты
и перезапуск сервера. Он служит стартовым значением; файловые инструменты и задания
всегда требуют явные `directory` и `branch` из контекста **данного чата**.
Отдельный чат не может незаметно перенаправить вашу запись через изменение
глобального выбора. Несовпадение фактической ветки останавливает операцию.
Если выбранный каталог удалили, карточка сообщает об этом и позволяет выбрать другой.

Грязная ветка не переключается автоматически. Нет скрытых stash/reset/force.
Для каталога без Git используется пустая `branch`, работа с файлами доступна.
Linked worktrees, submodules с `.git`-файлом и detached HEAD в этой версии
отклоняются: нужен обычный checkout с локальной веткой.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `pc_open_workspace_picker` | Карточка выбора и сохранённый каталог |
| `pc_capabilities` | Обнаруженные программы, sandbox и политика сети |
| `pc_get_workspace` | Сохранённый каталог и фактическая текущая ветка |
| `pc_directory_tree` | Дерево: до 300 папок, глубина до 5 |
| `pc_list_directory` | Файлы/папки, фильтр и пагинация |
| `pc_inspect_workspace` | Ветки и статус Git перед выбором |
| `pc_select_workspace` | Сохранить каталог, переключить/создать ветку |
| `pc_read_file` | Текст и SHA256 ревизия файла |
| `pc_write_file` | Запись с проверкой ревизии; `new` для создания |
| `pc_delete_file` | Удалить один файл с проверкой ревизии |
| `pc_start_job` | Асинхронная сборка, тест или проверка без сети/секретов |
| `pc_request_run` | Подготовить smoke/app/git/gh/сетевую команду, показать подтверждение |
| `pc_approve_run` | Только UI: подтвердить одноразовым приватным nonce |
| `pc_job_status` | Статус, новый вывод, итог и хвост журнала |
| `pc_cancel_job` | Отменить задание и остановить группу процессов |
| `pc_list_jobs` | Последние 50 заданий без журналов |

Пример аргументов для тестов:

```json
{
  "directory": "my-app",
  "branch": "feature/my-task",
  "args": ["go", "test", "./..."],
  "purpose": "test",
  "cwd": ".",
  "seconds": 300
}
```

`args` — массив executable + arguments. Неявного выполнения строки через shell
нет. Если нужен pipe или скрипт, явно используйте, например,
`["bash", "-lc", "go test ./... && go build ./cmd/app"]`.

После реализации и тестов модель должна спросить, запускать ли smoke/app.
`pc_request_run` показывает каталог, ветку, argv, срок, сеть и наличие
GitHub-токена. **До нажатия «Разрешить запуск» команда не выполняется.**
Одноразовый nonce находится только в `_meta` для UI, скрыт от модели;
инструмент подтверждения имеет `ui.visibility=["app"]`.
Если клиент не поддерживает MCP Apps или не передал приватные метаданные,
такой запуск блокируется. Булева галочка от модели не заменяет нажатие пользователя.
Карточка после подтверждения показывает статус и журнал, её «Отменить» останавливает процесс.

`purpose` описывает намерение, но сервер не умеет доказать, что произвольный
тестовый скрипт никогда не запускает приложение. Тесты и сборки могут изменять
файлы внутри sandbox. Инструкции запрещают модели обходить подтверждение
через смену `purpose`; это правило поведения, не анализ исходного кода.

## Git и gh

Git-операции доступны как команды внутри того же sandbox, с подтверждением:

```json
{
  "directory": "my-app", "branch": "feature/my-task",
  "args": ["git", "diff", "--stat"],
  "purpose": "git", "seconds": 30
}
```

Таким же образом доступны `git add`, `git commit`, `git log`, `git init` и т. п.
Для коммита задайте автора в локальной конфигурации проекта или явно через
`git -c user.name=... -c user.email=... commit ...`: глобальный `~/.gitconfig`
в sandbox не подключается. Смена/создание ветки через `pc_select_workspace`
предпочтительнее произвольной команды Git, поскольку проверяет dirty state.
Force/reset/stash не выполняются сервером автоматически.

Если установлен `gh`, для GitHub-операций можно отдельно настроить:

```bash
read -rsp 'GitHub token: ' PC_MCP_GH_TOKEN; echo
export PC_MCP_GH_TOKEN
./pc-mcp --root "$HOME/projects" --allow-network
```

Пример `pc_request_run`:

```json
{
  "directory": "my-app", "branch": "feature/my-task",
  "args": ["gh", "pr", "list", "--repo", "OWNER/REPO"],
  "purpose": "gh", "network": true, "credential": true, "seconds": 60
}
```

Токен передаётся только в явно подтверждённые `git`/`gh`-задания. Обычные тесты/сборки
его не получают. Для `git push/fetch` с `credential:true` также нужен установленный
`gh`: сервер задаёт `gh auth git-credential` как временный helper, без записи
токена в argv или `.gitconfig`, и отключает проектные hooks в таких заданиях.
Используйте HTTPS GitHub remote; SSH-ключи хоста не подключаются.
Установленный на хосте `gh auth login`, SSH agent, `~/.ssh` и
Git credential helpers не импортируются автоматически. Выдайте отдельный
GitHub token с минимальными нужными правами. В журнале заменяется его
случайно выведенное буквальное значение; кодирование/сознательный экспорт
секрета такой заменой не предотвращается.

## Сеть, окружение и ограничения

По умолчанию у процессов нет сети. Для скачивания зависимостей/gh нужен
`--allow-network` при запуске сервера, затем `network:true` у конкретного
задания **и подтверждение пользователя**. Без флага сервер отклоняет запрос.
Когда сеть разрешена, процесс видит сеть ПК, включая доступные ему локальные
адреса; сетевого allowlist по доменам в этой версии нет.

Процессы видят выбранный проект/checkout на запись, отдельный постоянный cache,
read-only системные программы и указанные SDK. Домашний каталог создаётся пустым,
`/tmp`, PID/IPC/UTS/user namespaces изолированы, `/proc` показывает sandbox.
Окружение пересоздаётся: ключ туннеля, токены приложения, SSH/DBus-сокеты и
переменные хост-сессии не передаются. Directory FD, используемый для безопасного
bind проекта, закрывается до запуска пользовательской команды.

Владельцу нужно держать секреты вне разрешённых проектов и SDK-папок.
Файловый API защищён `os.Root`: `..`, абсолютные пути, выходящие симлинки и
доступ к `.git` через файловые инструменты отклоняются. Для выбора проекта
используются настоящие папки, не симлинк-алиасы. Файлы только обычные, до
512 KiB; запись требует ожидаемую ревизию и использует атомарное переименование.
Ревизия предотвращает устаревшие записи клиента; внешние редакторы/Git на ПК
не участвуют в блокировке сервера, поэтому возможен обычный конкурентный доступ.

Одновременно выполняется **одно** задание. Пока оно работает, сервер запрещает
изменения файлов и смену веток/выбора. Есть wall-clock deadline, CPU deadline,
ограничение 1024 файловых дескрипторов и остановка всей группы процессов.
`--max-seconds` по умолчанию 900, максимум 86400; отдельное задание по умолчанию
300 секунд. У длительных приложений тоже конечный срок.
`GOMAXPROCS=2` задан для сервера и Go-процессов. Это число одновременно исполняемых
Go-потоков, а не общий лимит дочерних процессов. Жёсткие RAM/PID/disk quotas
и seccomp allowlist не реализованы; bubblewrap даёт файловую/namespace-изоляцию.

На иных ОС бинарник можно собрать, и файловые инструменты доступны; **запуск
команд пока реализован только для Linux**. Он не переключается автоматически
на небезопасный режим. Для Windows/macOS нужен отдельный sandbox backend.

## Вывод и задания

Задания не держат MCP-вызов до конца тестов. Старт возвращает ID; модель
опрашивает `pc_job_status` с `after=output.cursor` предыдущего ответа.

- Сохраняются первые **100 записей**, но не больше **32 KiB текста**, обоих потоков,
  объединённых по порядку приёма.
- Во время выполнения последующие записи подавляются в ответах, но оба потока
  непрерывно читаются — заполненная pipe не блокирует приложение.
- После окончания добавляются последние **10 записей** в пределах **8 KiB текста**,
  количество пропущенных,
  статус/ошибка, exit code для обычного завершения и время начала/завершения.
- Строка без newline разделяется на куски до 4096 байт с `truncated=true`:
  мегабайтная строка не раздувает память. Записи помечены `stdout`/`stderr` и
  sequence. Промежуточный хвост не отправляется в каждом poll.
- `after=0` позволяет повторно прочитать сохранённый журнал. Это первые+последние
  записи, не полный лог; полного бесконечного файла журнала нет.
- В памяти хранится до 50 заданий. Они доступны из нового чата через list_jobs,
  но не переживают перезапуск; сервер останавливает выполняющиеся задания
  при корректном shutdown. Завершённые журналы/результаты на диск не сохраняются.

Сервер не отправляет сам сообщения в чат. Карточка подтверждённого запуска
показывает вывод опросом; модель получает вывод через status tool. Это работает
без предположения, что ChatGPT принимает бесконечные streaming-уведомления.

## Проверки и локальный режим

```bash
make check
# На настоящем Linux-хосте с актуальным bubblewrap; отсутствие изоляции = ошибка:
make test-pc-sandbox
# Для локального MCP-клиента или диагностики, без туннеля/ключей:
./pc-mcp --root "$HOME/projects" --transport stdio
```

В stdio-режиме stdout занят MCP, диагностические сообщения идут в stderr.
SIGINT/SIGTERM останавливают клиент туннеля и выполняющиеся задания.

Тесты проверяют обходы путей, ревизии, dirty/stale branch, сохранение выбора,
lease на время задания, отмену, ограничение вывода без newline, stdout/stderr,
приватное подтверждение, UI и реальный обмен MCP через официальный tunnel SDK
с локальным mock control plane. Linux-интеграция отдельно проверяет filesystem
confinement, отсутствие credential env/host FD и отмену дочерних процессов;
без доступного bubblewrap она пропускается в обычном наборе, но обязательна
для `make test-pc-sandbox`.

## Архитектура

| Каталог | Ответственность |
|---|---|
| `cmd/pc-mcp` | Точка входа и GOMAXPROCS |
| `internal/pc/app` | Жизненный цикл сервера и встроенного официального Go-туннеля |
| `internal/pc/config` | Только настройки владельца ПК |
| `internal/pc/files` | Rooted файловый API, пределы и ревизии |
| `internal/pc/workspace` | Выбор, сохранение, Git и write lease |
| `internal/pc/sandbox` | Linux bubblewrap, чистое окружение, отмена процессов |
| `internal/pc/jobs` | Асинхронные задания, подтверждения, bounded output |
| `internal/pc/tools` | Типизированные инструменты/ресурсы MCP |
| `internal/pc/ui` | Встроенные MCP Apps карточки и JSON-RPC bridge |

Функции PC не смешаны с GitHub OAuth/API. Туннель является транспортом,
workspace отвечает за выбор/ветки, jobs — за выполнение и вывод.
